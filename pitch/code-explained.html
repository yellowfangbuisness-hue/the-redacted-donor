The Redacted Donor

How the code works: a guide for the team, written so that someone who has never opened the project can follow it.

The Redacted Donor is a 3D detective game about organ trafficking that runs in a web browser. You play Mateo, a man tricked by a fake job agency, and the detective who follows the evidence he left behind. The whole game is one file, index.html, built from about 8,800 lines of JavaScript. This guide explains what each part does, how the parts talk to each other, and where to look when you want to change something.

1. The big picture

The game is written in plain JavaScript with one library, Three.js, which draws 3D graphics in the browser. There is no game engine underneath it, and there are no 3D model files: the rooms, the furniture, the characters and the documents are built and painted by code when the game starts. The only things made outside the code are four illustrations and the recorded sounds and voice lines, which the build embeds in the page. That is why the game ships as one file, plus a second one that is only needed for hand tracking.

A small build script glues everything together. It reads the source files, bundles them with a tool called esbuild, embeds the artwork and the recorded sounds as text, and writes index.html. The same file is then wrapped three ways: opened directly in a browser, placed inside a Mac app, or copied into a Windows folder with a launcher.

Figure 1. From source files to the three ways of running the game.
Words used in this guide. A module is one source file. A frame is one picture drawn on screen; the game draws 60 or more a second. A shader is a small program that runs on the graphics card for every pixel. State is the set of facts the game remembers: which case you are on, what you have found, your score. Code shown in this guide is copied from the source and laid out for reading; three dots mark lines that were left out.

3. What happens in one frame

The heart of the game is one function, frame(now) in game.js. The browser calls it before every picture it draws. Each call does these five jobs.

Figure 2. The five jobs of every frame.

Everything that changes over time uses the time since the last frame, called dt. Walking, for example, moves the player by speed times dt. That makes the game run at the same pace on a 60 Hz laptop and a 240 Hz gaming screen: the faster screen simply gets more, smaller steps.

The loop also protects weak computers. keepPace() watches the average frame time. If frames are slow for two seconds it draws the picture a little smaller (down to 60% of full size) and scales it up, and it steps back up when the machine recovers. A machine that keeps up never sees a change.

function keepPace(real) {
  if (real <= 0 || real > .15 || document.hidden || inputMode === 'spatial') return;
  // a running average of the frame time, in milliseconds
  pace.avg += (real * 1000 - pace.avg) * .05; pace.t += real;
  if (pace.t < 2) return;                                      // decide once every two seconds
  pace.t = 0;
  const next = pace.avg > 26 ? Math.max(.6, pace.scale - .1)   // slow: draw smaller
             : pace.avg < 12.5 ? Math.min(1, pace.scale + .1)  // fast again: draw bigger
             : pace.scale;
  if (next !== pace.scale) { pace.scale = next; resize(); }
}

4. The story rules and the save

The game always knows which stage of the story it is in. A stage decides who you are, what you can interact with, and what happens next. The list is in campaign.js:

const stages = ['contract','street','detective','memory','lock','recoverKey','closet',
                'verify','board','gate','glass','radio','strip','end','gameOver'];
Figure 3. The stages of the story.

Two details the figure simplifies. After Mateo's six leads, case 1 has the detective open a locked drawer (lock), case 2 has them fetch a key and open the supply closet (recoverKey, closet), and case 3 goes straight to verify. And from any case, losing every composure bulb puts the game in gameOver; Retry restarts that case with the evidence you had when it began.

The rules themselves are short, plain functions that take the state and change it. They have no graphics in them, which is what makes them easy to test. Scoring is a good example. Every reward has a name, and a reward can only be given once:

export function grant(s, key, points) {
  if (s.awards.includes(key)) return 0;      // already given: nothing happens
  s.awards.push(key); s.score += points;
  return points;
}

casebook.js holds the data those rules work on. Each lead says when it can be found and what must come first, for example stamp: { shift: 'day', after: ['registration', 'ledger'], ... }. memoryTasks(state) reads that table and returns the leads that are open right now, which is all the game needs to decide what you may interact with.

The clock

A full day is 96 seconds of play, so each day or night shift is 48 seconds (shifts.js). Some leads only show by day and some only at night. The same file gives the window guard his timetable.

Saving and loading

persist() in game.js writes the state, plus where you are standing, into the browser's storage under the name redacted-donor.case.v1. Loading goes through readRun(), which trusts nothing: a save can come from another device or from a transfer code somebody else made, so every field the game uses is checked and repaired first.

  s.exhibits = ints(s.exhibits, i => !!evidence[i]);     // drop evidence that does not exist

5. Drawing the world

Rooms made from boxes

room.js builds the clinic out of simple shapes. A helper called box(x, y, z, width, height, depth, colour) adds one block; plane(texture, ...) adds a flat painted surface. Thousands of these would be slow to draw one by one, so bake() merges every shape that shares a material into a single mesh. The fixed parts of a room are then drawn once per material instead of once per shape.

Textures are painted by code on an HTML canvas when the game starts (InkTextureFactory.make()): floorboards, striped wallpaper, forms, tags. Nothing is downloaded.

Normal maps on walls and floor

A normal map is a second texture that records which way each tiny patch of a surface leans. With it, a flat wall can catch light as if its mouldings were really raised. relief() works one out from the painted texture itself: darker paint is treated as lower, and the slope between neighbouring pixels gives the lean.

The walls and floor are unlit (their colours are exactly what was painted), so the normal map is used in a careful way. A few lines added to their shader brighten or darken each pixel by how far it leans toward the window:

// the lean stored in the normal map, as a direction
vec3 m = texture2D(reliefMap, vMapUv).xyz * 2.0 - 1.0;
// brighten or darken the painted colour by how far that direction points at the light
diffuseColor.rgb *= clamp(1.0 + 1.15 * dot((T*m.x + B*m.y) * inv, reliefLight), 0.5, 1.5);

A flat pixel has no lean, so it is multiplied by exactly 1 and keeps its colour. Only board gaps, panel edges and grain gain light and shadow.

The ink look

renderer.js draws in two steps. First the 3D scene is drawn into an off-screen picture, along with a depth picture that records how far away each pixel is. Then one large shader, the ink pass, turns that into the final image. It finds edges by looking for sudden jumps in depth and draws dark outlines there, adds paper grain, tints the scene for day or night, adds sunbeams and dust, and, during a scene change, lets black ink close in from the edges and drip from the top.

Two details are worth knowing:

  • Puzzles are drawn on top. An open puzzle is drawn in its own pass and laid over the room, so a desk or a wall can never poke through it (setOverlay()).
  • Resolution is capped. The picture is never drawn larger than about 1600 by 1000 pixels, and keepPace() can lower it further on a slow machine.

Measured on an Apple silicon Mac at 1280 by 800 with the frame limit off: 2.7 to 4.4 ms a frame, 30 to 264 draw calls. The lab is the heaviest room.

6. Characters and guards

Paper cut-outs that move

The recruiter, the enforcer, the guards and the orderly are flat drawings that always turn to face the camera, like paper puppets standing in a 3D room. sprites.js animates them without any new artwork. Each character's original drawing function takes a pose (how far the body bounces and leans, where the legs are in the stride, how the head tilts) and bends its own drawing to match.

  • makeSheet() paints a sprite sheet once: 20 small pictures of the character (2 idle, 6 walking, 6 running, 4 interacting, 2 looking).
  • SpriteSheetAnimator shows one of them at a time by sliding the texture, 12 pictures a second whatever the frame rate, which gives the hand-drawn feel.
  • Actor adds a body: it walks to a list of points and cannot pass through furniture, because each step is checked against the rectangles in floorplan.js.
  • Cutscene runs steps in order: walk here, wait, act, turn. The opening scene in props.js is written this way.

Guards

stealth.js runs the guards who patrol the lab and the dispatch office. Each guard is always in one mode: walking his route, pausing to look around, going to check a noise, chasing, searching, or returning. The rules that move him between modes are what make him feel alert:

He notices you whenHow it works
He sees youYou are inside his sight cone (45 degrees to each side, 4 m by day, 3.5 m at night), nothing tall is between you, and you are not crouched behind cover.
He hears youWalking carries 1.7 m and running 4.5 m. Crouching or standing still is silent, and the crepe soles from the shop halve both distances.
You are too closeWithin 1.1 m he senses you whichever way he faces.
Another guard callsA guard who spots you alerts the others within 10 m.

Once he has seen you he chases, runs on to where he last saw you, searches there, and stays wary for a while. Throwing something (a beaker, a ledger) makes a crash that pulls the nearest guard away. All the numbers are named constants at the top of the file, so they are easy to tune.

7. Hands-on puzzles

Every interaction in the game is something you do with your hands rather than a button you press: you pull a drawer, turn the wheels of a padlock, piece a torn card together, sweep a UV lamp across glass. hands.js contains 19 such views.

They all work the same way. When you interact with something, tactileFor(id) in game.js looks up which view to open and with what options. openHands() moves the camera in and builds a small 3D board in front of the object. Each view is a function that adds shapes to that board and says how they respond to being grabbed:

r.grab(handle, {
  down: (p) => { y0 = p.y; o0 = open; },                     // remember where the pull started
  move: (p) => {
    if (r.finished) return;
    open = clamp(o0 + (p.y - y0) / 150, 0, 1); apply();      // the drawer follows the hand
    r.sfx('screech', open);                                  // and squeals as it moves
  },
  up: letGo,                                                 // far enough open? then it is done
});

Positions are in "board units": the board is 560 units wide and 320 tall. Mouse, controller and tracked hands all arrive as the same three events (down, move, up), so a puzzle is written once and works with every input. When a view calls r.finish(), the game runs whatever that interaction unlocks in the story.

8. Hand tracking

With hand tracking on, the game watches your hand through the webcam. Closing your hand grabs, opening it lets go, moving it toward a screen edge turns your head. The picture never leaves the computer. All of this is in spatial.js, and it is the most intricate part of the project, so this section goes step by step.

Figure 4. From the camera to the game.

Step 1: finding the hand

Google's MediaPipe hand model looks at each camera picture and returns 21 points for every hand it finds. Reading one picture takes 10 to 25 ms, which would make the game stutter if it ran in the game's own loop. So by default it runs in a worker, a second thread: the game hands it one picture, carries on drawing, and collects the answer when it is ready. If a browser cannot run the model that way, or it turns out slower there, the game switches by itself to running it in the main loop, and Pause lets the player choose.

The model's own files (its code, a WebAssembly program and the trained model, about 17.6 MB together) are packed into hand-tracking.js beside the game, so tracking starts in under a second and needs no internet.

Step 2: steadying the points

Raw points jitter. Each coordinate goes through a One-Euro filter, which smooths heavily while the hand is still and hardly at all while it moves fast, so the pointer is both steady and quick:

filter(x, t, k = 1) {
  ...
  // how fast is it moving?
  this.dx += alpha(this.dCut) * ((x - this.x) / dt - this.dx);
  // the faster it moves, the less it is smoothed
  this.x  += alpha(this.minCut + this.beta * k * Math.abs(this.dx)) * (x - this.x);
  return this.x;
}

Step 3: reading gestures

The Track class follows one hand and measures it in ways that do not depend on how far it is from the camera, by dividing every distance by the length of the palm. A pinch is the thumb tip close to the index tip. A grip is the four fingertips, on average, close to the wrist. A knock is a fist growing quickly in the picture, which means it is coming toward the camera.

Each gesture switches on and off through a Latch, which needs the condition to hold for a moment and uses a tighter threshold to engage than to release. That stops a trembling hand from flickering between grabbed and not grabbed.

Step 4: making sense of two hands

The Gestures class decides which hand is the pointing hand and keeps it that way even when the model's left and right labels flicker. It also guards against the cases a camera model handles badly:

SituationWhat the engine does
Hands touch or overlap (a clap)Nothing is trusted: the pointer holds still, a grab lets go, and no knock fires. When the hands part, they are told apart afresh.
The model reports one hand twiceIt is treated as one hand, because two real hands cannot arrive on the same spot without having been seen approaching.
A second hand rests in view, curledIt does not block the first hand from grabbing. Two closed hands only mean "turn this" when something can be turned.
The hand moves too fast to readNo grab starts on a blurred hand. One already held is kept, even if the hand vanishes for up to 0.45 s.
Fingers close or openThe palm slides a little as they do. If the hand was at rest, the grab or release lands where it was holding still.

Step 5: from hand position to screen position

The pointer follows the centre of the palm, which stays put when the fingers close. The four-step setup records where your hand rests and how far it reaches, and that area is stretched to cover the whole screen. Because the camera, the model and the filters all run a little behind the real hand, the pointer is run slightly ahead of it, but never past where the hand has been seen to be, so it cannot overshoot a hand that stops.

Step 6: gliding between pictures

The camera gives 30 or 60 pictures a second, but a gaming screen draws 144 or 240. Without help the pointer would move in visible steps. The Glide class fills the gaps: between pictures it carries the pointer on at the speed it was last seen moving, and blends each new picture in over a few frames.

run(now) {     // where the last picture's pointer has got to by now
  const dt = Math.min(Math.max(0, now - this.since), 45) / 1000, m = this.m;   // 45 ms at most
  return { x: this.p.x + (m ? m.vx * dt : 0), y: this.p.y + (m ? m.vy * dt : 0) };
}

Measured with a real photo of two hands fed in as the camera: both hands found at 30 pictures a second, the pointer moved on every drawn frame, and the game kept 60 frames a second with the background thread against about 50 without it.

Step 7: what the game does with it

pointerInput(frame) in game.js receives the result on every frame. Over a menu, a grab is a click. In a puzzle, a grab is a mouse press at the pointer, a turn of the wrist turns a dial, and a fist pushed at the camera breaks glass. In the room, a grab is the interact key, and moving the hand past its comfort zone turns the view. A controller's stick uses the very same function, which is why controller support needed so little code.

9. Sound and voice

sound.js uses the browser's WebAudio system. Sounds come from two places. Recorded files in src/audio/ are embedded in the page by the build; when you press Begin they are unpacked one at a time, smallest first, so clicks and the first voice lines are ready at once. If a recording is missing, the same cue is synthesised: a short burst of filtered noise for a footstep, a falling tone for a latch.

  • play(name, volume) plays a recorded sound; several takes of the same name (clink, clink-1) are chosen at random.
  • say(...ids) plays voice lines one after another, and a new line cuts the old one short, so two never talk over each other. There are 54 recorded lines.
  • jazz(on), tension(on) and the ambience are long loops that fade in and out. Jazz plays for the detective, the tension track when a guard has seen you.
  • The heartbeat is driven by one number, pulse, which game.js works out each frame: 0 when you are safe, rising to 1 as a guard nears, notices you and closes in. It sets both how fast and how loud the beats are.

Subtitles and speech stay in step because the game speaks by text: speak(text) looks for a known phrase in the line being shown and plays the matching recording.

10. Online records and security

The game is fully playable offline. cloud.js adds three optional things through a hosted database (Supabase): an account, a copy of your save, and a leaderboard. The game never waits for the network: results go into a local queue and are sent when a connection is there.

The database does not trust the game either. Its tables cannot be written directly; every change goes through a database function that checks who is asking and whether the request is plausible (supabase/schema.sql).

Protections in the page itself

  • Page policy. The build writes a Content-Security-Policy into the page. The browser will only run the script the build produced (matched by a fingerprint) and the hand-tracking files, so text typed by other players can never run as code.
  • Escaping. Any text that came from outside (a leaderboard name, an email) passes through esc() before it is shown.
  • Save checking. Described in section 4: a damaged or hostile save is repaired or refused, never trusted.
  • Camera. Hand tracking is off until you turn it on. Pictures are read on the device and never stored or sent. The Mac app grants the camera only to the game's own page.

One rule that keeps the project healthy. The story rules (campaign.js, casebook.js, shifts.js) never touch graphics, and the graphics never decide the story. If you keep new code on the right side of that line, the tests keep working and a change in one place does not break another.
